AIRS Time-Series Expansion Roadmap

5초 센서 데이터에서
운영 판단까지 가는 길

AIRS는 이미 MQTT로 들어오는 온도, 습도, CO2, 재실, Wi-Fi RSSI 데이터를 InfluxDB에 저장한다. 다음 단계는 이 데이터를 단순 조회가 아니라 집계, 특징 추출, 알림, 예측까지 확장하는 것이다.

포트폴리오 핵심 문장: “5초 단위 IoT 시계열 데이터를 운영 가능한 상태 판단 API로 전환한 백엔드 파이프라인을 구축했다.”

왜 지금 확장이 필요한가

1

데이터가 너무 많아진다

5초마다 저장하면 노드 1개가 하루 약 17,280개 포인트를 만든다. 노드가 늘어나면 장기 조회 API가 급격히 무거워진다.

2

현재값만으로는 판단이 약하다

CO2 950ppm은 아직 보통이지만, 10분 동안 180ppm 상승했다면 곧 환기 필요 상태가 될 수 있다.

3

운영자가 원하는 건 숫자가 아니다

앱/웹에는 “환기 필요”, “Wi-Fi 약함”, “센서 이상”, “냉난방 낭비 의심” 같은 판단 결과가 필요하다.

MQTT topic: airs/node/node_01/telemetry { "node_id": "node_01", "temperature_c": 24.3, "humidity_pct": 53.2, "co2_ppm": 842, "pir_detected": 1, "mmwave_detected": 0, "wifi_signal_dbm": -58, "sensor_status": { "dht22": "OK", "scd41": "OK" } }

추천 우선순위

P0

period별 adaptive window query

1일 조회와 1년 조회에 같은 5초 데이터를 반환하면 앱 그래프와 네트워크가 버티기 어렵다. 조회 기간에 따라 자동으로 window를 바꾼다.

1일: 5분 평균 1개월: 2시간 평균 1년: 1주 평균
P0

raw / rollup / retention 설계

5초 원본은 짧게 보관하고, 장기 그래프는 1분/1시간/1일 집계 bucket을 조회한다. 저장 비용과 응답 속도를 동시에 관리한다.

raw: 7~30일 1m rollup: 6개월 1h rollup: 2년
P1

sliding window feature 생성

현재 CO2 값 하나보다 최근 변화량이 더 중요하다. `co2_rate_10m`, `temp_rate_30m`, `co2_over_1000_minutes`를 만든다.

+120
co2_rate_10m
10분 전보다 CO2가 120ppm 상승
P1

duration-based alert detection

한 번 튄 값이 아니라 “일정 시간 지속된 문제”만 alert로 만든다. 운영자가 신뢰할 수 있는 알림을 만드는 핵심이다.

CO2 1000ppm 10분+ Wi-Fi -85dBm 3회+ 30초 telemetry 없음
P1

sensor data quality / anomaly detection

센서가 고장나면 데이터 기반 판단 전체가 흔들린다. stuck, 비정상 급변, DHT22/SCD41 불일치 같은 데이터 품질 문제를 잡는다.

stuck value 급격한 점프 센서 간 불일치
P2

CO2 forecast

현재 상태가 아니라 10~30분 뒤 위험을 예측한다. ML 없이도 최근 기울기 기반 선형 예측부터 시작할 수 있다.

futureCo2 = currentCo2 + co2Rate10m * 1.5 842 + 120 * 1.5 = 1022ppm => 지금 환기 권장
P2

공간별 baseline 비교

강의실, 도서관, 연구실은 정상 패턴이 다르다. 같은 요일/시간대의 평소 패턴과 비교하면 더 정확한 이상 판단이 가능하다.

K301 평일 14시 평균 R904 야간 패턴 공간별 정상 범위
P3

ML 기반 이상탐지 / 예측

충분한 데이터가 쌓인 뒤 Python AI 서버나 batch 학습으로 확장한다. 이번 단계에서는 rule-based feature 파이프라인이 먼저다.

포트폴리오에서 어필 가능한 문장

AIRS는 5초 단위 IoT 센서 데이터를 InfluxDB에 저장하고, 조회 기간에 따라 자동 downsampling하여 응답량을 최적화했다. 또한 sliding window 기반 feature(co2_rate_10m, temp_rate_30m 등)를 생성해 환기 필요, 재실 상태, Wi-Fi 이상, 센서 이상 상태를 판단하고, MySQL snapshot과 alert 테이블에 반영하는 시계열 분석 파이프라인을 구축했다.
추천 구현 순서: 먼저 P0로 조회 성능과 저장 구조를 안정화하고, P1에서 feature와 alert를 붙인다. P2/P3 예측·ML은 데이터가 충분히 쌓인 뒤 진행하는 것이 현실적이다.
